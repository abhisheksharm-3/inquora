# Inquora UI: scope and sizing

Date: 2026-08-25
Status: scoping only. No visual direction is decided here.
Related: `.polaris/specs/2026-08-25-non-ui-core-design.md`, `docs/adr/0001`–`0004`

## What this document is for

Two jobs. First, to size the UI rebuild. Second, and more urgently, to surface the UI decisions
that change the backend schema **before Phase 1 freezes it**, since Phase 1 is the only
irreversible step in the other plan.

Design context now exists: `PRODUCT.md` and `DESIGN.md` at the repository root, written from the
teach interview on 2026-08-25. The palette and the second visual register stay open on purpose and
are decided in the shape step from rendered variants, not chosen in a document.

## The "sluggish" claim, measured

The instinct is right. Here is what it is caused by, in order of impact.

### A WebGL shader canvas is mounted on the loading screen

`Dither.tsx` is 390 lines of `three` + `@react-three/fiber` + `@react-three/postprocessing`
running a continuously animating fragment shader. It is mounted in six places:

```
src/app/loading.tsx              ← the loading screen
src/app/error.tsx
src/app/not-found.tsx
src/app/page.tsx
src/app/(dashboard)/layout.tsx   ← every authenticated page
src/components/layout/Layout.tsx
```

Mounting a WebGL scene inside `loading.tsx` means the heaviest thing in the bundle initializes at
the exact moment the browser is busiest. It runs on every dashboard route through the layout, so it
never unmounts during a session, holding a GPU context and an animation loop for a decorative
background.

`three` publishes a minified bundle in the several-hundred-kilobyte range; the exact cost to this
project is unmeasured because `node_modules` is not installed locally. Measuring it is task one of
the rebuild, not an assumption to build on.

### Almost everything is a client component

```
"use client" files : 63
total .tsx files   : 89
server components  : 9
```

Seventy-one percent of the component tree ships to the browser and re-renders there. Next 16.3's
entire performance model — cached shells, partial prefetching, streamed dynamic content — assumes
the opposite ratio.

### Manual memoization the compiler already does

```
useCallback : 53
useMemo     : 19
useEffect   : 22
useState    : 34
```

`babel-plugin-react-compiler` is enabled in `next.config.ts`. Seventy-two of those `useCallback` and
`useMemo` calls are work the compiler now performs, kept alive by hand, adding dependency arrays
that are themselves a bug surface.

Against that, the React 19 APIs designed for this app are nearly unused:

```
useActionState     : 0
useDeferredValue   : 0
useOptimistic      : 1
useTransition      : 1
```

### Three state systems own one message list

`useMessages.ts` runs TanStack Query, `useOptimistic`, and a Supabase realtime channel
subscription over the same array, reconciled by hand — including a reducer that finds an optimistic
message by an `id.startsWith("temp-ai-")` string prefix. Any of the three can win a race.

### The largest UI file is a loading skeleton

`SettingsLoadingSkeleton.tsx` is 421 lines — larger than `ChatInterface.tsx` at 290. A placeholder
shown for a few hundred milliseconds is the biggest component in the codebase.

### Deprecated React idioms

Two files use `forwardRef`, deprecated in React 19 in favour of `ref` as a prop. Four use
`<Context.Provider>` rather than `<Context>`.

## Library strategy: what to stop hand-rolling

### assistant-ui — adopt

`@assistant-ui/react` ships, as unstyled Radix-style primitives: Thread, Composer, Message,
ActionBar, BranchPicker, attachment handling with drag-drop and paste, message editing and
regeneration, branch navigation, tool-call rendering, a chain-of-thought accordion, **citation and
source rendering**, suggested prompts, and per-message timing metrics including time to first
token.

Every one of those is either hand-rolled here today or missing. Because the primitives are
unstyled, adopting them costs nothing in visual distinctiveness — which matters, since a library
that imposed its own look would guarantee the templated feel you want to escape.

Integration is through `ExternalStoreRuntime`, which lets an existing state owner stay in charge, so
TanStack Query keeps owning server state rather than being replaced.

### AG-UI — rejected, and the reason changed

The first version of this document deferred AG-UI because the backend had no tool calls. Tool
calling is now a requirement, so that reason is void. The decision stands anyway, for a better
reason.

The stack is LangChain on the server and assistant-ui in the browser, and `useLangGraphRuntime`
already reads LangChain's own stream — streaming text, tool calls, interrupts, cancellation.
Inserting AG-UI means translating LangGraph events into AG-UI events on the server and AG-UI events
into assistant-ui parts in the browser: two hand-written mappings, both able to drift, in place of
none.

AG-UI earns its place when one frontend speaks to several different agent backends, or when a third
party consumes the agent. Neither is true here. See `docs/adr/0005`.

### tRPC — skip, and this one is worth arguing

tRPC solves keeping an API contract in sync between client and server without codegen. That problem
is already solved here three separate times:

- **Server Actions** are natively typed across the boundary, with no router and no client bundle.
- **The SSE endpoint** shares a Zod schema between handler and client, per the backend design.
- **Supabase types** are generated from the schema by `supabase gen types`.

Adding tRPC means a router layer, a client bundle, and a second way to call the server sitting
beside Server Actions, which cannot be removed anyway because forms and mutations use them. Next
16.3 is pushing the opposite direction: `'use cache'`, `cacheTag`, `updateTag`, and data fetching
inside Server Components.

You asked for less code. tRPC would add some. The recommendation is Server Actions for mutations,
TanStack Query for client-owned server state, shared Zod at the streaming boundary. Overridable, but
this is the honest reading.

## Next 16.3 and React 19: what to actually use

`next.config.ts` currently sets `cacheComponents: true` and `reactCompiler: true`. Everything else
below is unused.

| Feature | Where it applies here |
|---|---|
| `partialPrefetching: true` | Not enabled. Prefetches a route's shell for visible links. |
| `<Link prefetch={true}>` | Chat links in the sidebar and history, so a conversation resolves its `params` before the click. This is what "instant" means concretely. |
| `'use cache'` + `cacheLife` + `cacheTag` | Chat list, document list, settings. Keyed by id, tagged for expiry. |
| `updateTag` in Server Actions | Renaming or deleting a chat expires exactly the views that show it. |
| Nested `<Suspense>` | Message list resolves above citations, so the page settles top-down instead of shoving content around. |
| `<ViewTransition>` | Streamed message reveals, list morphs when a chat is deleted, directional slides between routes via `transitionTypes`. |
| `useActionState` + `useOptimistic` + `startTransition` | Sending a message. Replaces the hand-reconciled three-system approach in `useMessages.ts`. |
| `use(promise)` | Reading server-passed promises in client components without an effect. |
| `useFormStatus` | Composer send button state without prop drilling. |
| `ref` as prop | Deletes both `forwardRef` wrappers. |
| `<Context value={}>` | Deletes four `.Provider` usages. |
| Document metadata in components | Per-chat `<title>`, currently absent. |
| `preload` / `preconnect` | Warm the Supabase and embedding origins on first paint. |
| `@next/playwright` `instant()` | E2E assertions scoped to prefetched UI, so an instant-navigation regression fails CI. |
| `useOffline` | Reconnect banner for a dropped stream. **Experimental, not recommended for production** — evaluate, do not ship blind. |

Reference implementations worth reading before building: Vercel's `Huddle`
(github.com/aurorascharff/next16-team-chat), a Slack-like chat on Next 16.3 shipped in both TanStack
Query and SWR variants, and `Drop` (github.com/aurorascharff/next16-social-media) for cached route
data and streamed reveals.

## What this changes in the backend slice

Four findings, in urgency order. The first two must land before Phase 1 pushes migrations, because
Phase 1 rebuilds the remote database and is the only irreversible step.

### 1. `messages` needs a parent pointer, or branching is impossible

assistant-ui ships `BranchPicker`, message editing and regeneration as built-ins — the thing that
makes Claude and ChatGPT feel like tools rather than transcripts. All of it requires a message tree,
not a message list. The Phase 1 schema is about to freeze `messages` as a flat list ordered by
`created_at`.

Required change to `supabase/migrations/0004_chats_and_messages.sql`:

```sql
parent_id uuid references public.messages (id) on delete cascade,
```

plus an index on `(chat_id, parent_id)`. Retrofitting a parent pointer onto a live message table
later means backfilling 851 rows' worth of implied structure that was never recorded.

### 2. `chat_documents` needs ordering and an enable flag

Multi-document chat has an interface, not only a query. Documents appear in a list, so they need a
stable order; and "search only these two of my five" is the obvious first thing a user reaches for,
which is a per-chat toggle rather than removing the document from the chat.

Required change to the same migration:

```sql
position integer not null default 0,
enabled  boolean not null default true,
```

`search_chunks` then receives only the enabled ids, which needs no change to the function.

### 3. Ingestion progress needs an expected total

`documents.status` has four states, so the UI can show four words. A progress bar needs a fraction,
which means the extractor must record how many chunks it is about to write before embedding starts.

Suggested change:

```sql
expected_chunks integer,
```

Progress is then `chunk_count::float / nullif(expected_chunks, 0)`, and the existing trigger already
maintains the numerator.

### 4. The bespoke SSE contract is withdrawn

Resolved rather than open. The wire is LangGraph's own stream, read by `useLangGraphRuntime`, so
the four-event contract in the backend design is gone and nothing replaces it by hand. The one risk
to retire early is that `@assistant-ui/react-langgraph` is built against the LangGraph server API;
serving the same shape from a plain Next route handler is supported but unproven here. Phase 3
opens with a spike that streams one tool call end-to-end. See `docs/adr/0005`.

### 5. Decisions taken since the first draft

- **Branching: yes.** `messages.parent_id` and the `message_parts` table are in migration `0004`.
- **The dither background is deleted**, not confined. U2 becomes a deletion, and `three`,
  `@react-three/fiber` and `@react-three/postprocessing` leave `package.json` with it.
- **Register is both.** Every surface is in scope, landing page included, and rebuilding from
  scratch is preferred wherever that is cheaper than reworking.
- **Landing page anti-patterns, stated by the user:** no centred headline hero; no split hero with
  an animation on one side and text on the other. These are hard bans for the brand surface, and
  `impeccable`'s reflex-reject check applies on top of them.
